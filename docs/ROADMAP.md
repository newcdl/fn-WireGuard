## 一、现有能力盘点

### 1.1 功能模块地图

| 模块 | 用户可见能力 | 关键实现 |
|---|---|---|
| 数据面收敛 | 连接启停、设备下发、状态自愈 | `internal/wgback/`（`linux.go` netlink / `mock.go` 内存）、`internal/reconcile/` 10 秒收敛循环 |
| 路由安全 | 不改系统网络、可一键复原 | `routesafety.go` 纯函数铁规则、`policyroute.go` 专用策略表 `51888` + `ip rule` |
| 内网访问 | 设备能访问家里其它机器 | `natplan.go` 决策、`nat.go` 专用 nftables 表 `inet fn-wireguard`、六层自检 |
| 连接管理 | 创建/编辑/启停/导入导出 | `internal/service/interface.go`（跨连接冲突校验、地址端口自动错开） |
| 设备管理 | 二维码、上网方式、期限、配额、批量导入、新建向导 | `internal/service/peer.go`（`ImportPeers` 批量）、`engine.go` 期限与配额强制下线 |
| 密钥托管 | 私钥不落明文、可轮换 | `internal/secretbox/` AES-256-GCM、`wgkey` 密钥生成 |
| 配置生成 | wg-quick 风格配置、二维码 | `internal/wgconf/`、前端二维码渲染 |
| 实时监控 | 流量曲线、设备在线状态 | `internal/api` WebSocket + 前端 `stores/realtime.ts` + ECharts |
| 权限与审计 | 管理员/运维/只读、操作留痕 | `internal/api` 角色校验 + `internal/store` 审计表 |
| 系统维护 | 体检、修复、残留清理、重新应用 | `frontend/src/views/Maintenance.vue` + `internal/service/network.go` |
| 异常可见性 | 顶栏状态栏、全局横幅、行内提示 | `frontend/src/composables/useSystemHealth.ts`（唯一数据源） |
| 账号安全 | 动态口令二次验证、一次性恢复码、信任本设备 | `internal/totp/`（自实现 RFC 6238）、`sys_totp_challenge` / `sys_recovery_code` / `sys_trusted_device` |
| 帮助系统 | 每个配置项的「是什么/为什么/影响/例子」 | `frontend/src/constants/fields.ts`（`FieldTips` / 配置说明大全） |
| 全局搜索 | 顶栏一个入口搜连接与设备并跳转详情 | `frontend/src/components/GlobalSearch.vue` |
| 备份还原 | 整机配置备份、含/不含密钥 | `internal/service/config.go` + 前端「备份还原」 |
| 配置快照回滚 | 关键操作自动留档、查看差异、一键回滚 | `internal/service/snapshot.go` + 前端「系统设置 → 配置快照」 |
| 交付链路 | 双架构安装包、自动发版 | `scripts/build.sh`、`scripts/version.sh`、`.github/workflows/release.yml` |

### 1.2 已经做扎实的部分

1. **安全边界**：所有网络改动只落在自己创建的对象上，且都有穷举式单元测试（路由安全、内网访问决策、出口网卡选择）。
2. **故障自愈**：收敛引擎幂等 + 启动自愈，配置漂移会自动纠正；单条连接失败不阻断其它连接。
3. **可读的错误**：跨连接冲突、出口网卡探测、内网访问链路都直接给出「哪一层没过 + 怎么处理」。
4. **可追溯的版本**：版本号单一来源，tag 与 manifest 强校验。

## 二、下一阶段方向

当前版本已做到「基本可用」：能建连接、发设备、扫码连通、看状态、出问题能定位。**下一阶段不再堆功能，而是围绕三个方向做深**：

| 方向 | 含义 | 判断标准 |
|---|---|---|
| **更好用** | 少点几下、少想几步 | 常见任务的点击次数下降；新增流程有引导；配置项不需要查文档 |
| **更实用** | 覆盖真实使用中「不得不做」的事 | 能在界面内完成，不再需要 SSH 或手工改配置 |
| **体验更优** | 更快、更稳、更清楚 | 异常有原因、操作有反馈、长任务有进度、失败可重试 |

### 优先级判定原则

- **P0**：不做会让用户卡住，或现状与承诺不符（例如摆设设置项）→ 下一版必做
- **P1**：明显提升日常效率或覆盖高频场景 → 排入下一个次要版本
- **P2**：扩大适用范围或加固安全 → 视精力插入
- **P3**：锦上添花、依赖较多 → 放到 1.0 之后

## 三、功能清单（按优先级）

### P0 —— 0.7.0「访问控制与通知」（已完成）

> 主题：让「多人共用」可用，让「出问题第一时间知道」。两者都直接对应 1.3 里的缺口 1、2。
>
> **已完成**，四条验收（V1~V4）逐条落地，实际实现与规划的偏差见[十、0.7.0 偏差补记](#十070-偏差补记)。

#### P0-1 设备间隔离

- **预期目标**：一条连接内可以禁止设备互访，设备只能访问 NAS，不能访问彼此。
- **衔接现有功能**：复用内网访问的专用 nftables 表（`nat.go`）与「只匹配隧道网段」的约束，新增一条 `iifname 隧道 && oifname 隧道 → drop` 的前置规则。
- **依赖**：无（`nat.go` 已具备建表、清理、指纹去抖能力）。
- **验收**：见[八、验收标准](#八验收标准) V1。

#### P0-2 按设备划分访问范围

- **预期目标**：给单个设备指定「只能访问哪些网段」，替代现在「整条连接一刀切」。
- **衔接现有功能**：复用设备的上网方式模型（`route_mode` + `client_allowed_ips`）与 `wgconf` 配置生成；范围校验复用 `routesafety.go` 的网段重叠判定。
- **依赖**：P0-1（两者共用同一套访问控制规则与诊断）。
- **风险提示**：范围改动需要设备重新扫码，界面必须显式提示。
- **验收**：见 V2。

#### P0-3 事件通知（让 Webhook 真正生效）

- **预期目标**：设备上线/离线、连接异常、设备到期、配额用尽等事件推送到用户配置的地址。
- **衔接现有功能**：挂到收敛引擎已有的事件点（`engine.go` 中配额/到期的判定、`Diff` 动作流）；凭据复用 `secretbox`；设置项复用现有的 `notify_webhook` 字段（不再新增字段）。
- **依赖**：无；同时是 0.8「告警与日报」的前置。
- **硬性约束**：**必须异步发送**，绝不能拖慢 10 秒收敛循环。
- **验收**：见 V3。
- **0.7.1 追加（通知能力的收尾）**：
  1. 系统设置新增独立的「事件通知」页签（位于「接入设置」之后），与接入设置各自保存；
  2. 推送格式增加 **Markdown**：钉钉、企业微信与飞书按各自报文结构投递（飞书用交互式卡片，头部按级别上色），并解析响应里的错误码判断业务失败（这类失败原本藏在 HTTP 200 里）；
  3. 事件清单补齐到 **8 类**并按设备/连接/系统分组：新增「连接中断」「连接恢复」「配置下发失败」「残留网络自愈」；
  4. 事件开关的存储语义改为「记录被**明确关闭**的事件」，使以后新增的事件默认开启，避免「新事件静默不生效」；
  5. 界面显示**实际发出的内容**（截断）—— 接收端不显示消息时这是唯一可靠的线索。

#### P0-4 访问控制冲突诊断

- **预期目标**：设备范围、隧道网段、主机网段三者冲突时给出「谁和谁冲突、建议改成什么」，而不是静默失效。
- **衔接现有功能**：复用 0.3.1 的跨连接校验框架与 `useSystemHealth` 的异常清单展示。
- **依赖**：P0-1、P0-2。
- **验收**：见 V4。

### P1 —— 0.8.0「内网体验与管理效率」

#### P1-1 DNS 主机名解析（已完成）
- **目标**：连进来的设备能用「主机名」访问家里设备。
- **衔接**：NAS 作为隧道内 DNS，只监听隧道地址；下发 DNS 复用现有 `dns` / `dns_mode` 字段。
- **依赖**：P0-3（解析服务异常时需要通知）。
- **难点/风险**：见[七](#七技术难点与风险) R4。
- **实际实现**：自实现极简解析器 `internal/dnsserver`（**不引入 DNS 库**，避免增大二进制）：
  解析问题段 → 对用户登记的名字做 A 记录应答 → 其余查询原样转发上游 → 无上游时回 SERVFAIL；
  UDP 与 TCP 都提供（TCP 不是可选项：响应被截断时客户端会改用 TCP 重试）。
  监听地址只取**本应用连接的隧道地址**（绝不监听 0.0.0.0:53），因此不会与 NAS 上已有的 DNS
  （Docker/AdGuard）抢端口，也不碰系统 DNS 配置。开启后，下发给设备的 DNS 改指隧道地址，
  连接里原本配置的 DNS 成为解析器的上游。
  解析器跑在**特权代理**里（绑定 53 需要 `CAP_NET_BIND_SERVICE`，已在 systemd 单元中放开），
  随每次收敛对齐期望态、自愈监听；记录用 `dns_record` 表维护，界面在「系统设置 → 内网域名」管理。

#### P1-2 DDNS 自动更新对外地址（不做：飞牛系统自带）
- **原目标**：公网 IP 变化后自动更新「对外访问地址」。
- **结论**：**不做**。飞牛 fnOS 系统本身已提供 DDNS 能力，在本应用里再实现一套属于重复建设，
  还会多出一份需要用户托管的服务商凭据（即原风险 R5）。正确做法是引导用户到**系统设置**里配置 DDNS，
  本应用只负责把「对外访问地址」填成那个 DDNS 域名即可。
- **对规划的影响**：原依赖链 `P0-3 → P1-2 → P3 计划备份/巡检报告` 中的 DDNS 一环移除，
  这两项 P3 功能改为直接依赖 `P0-3`（已完成）。

#### P1-3 设备批量导入与新建向导（已完成）
- **目标**：一次导入多台设备（CSV/文本），新建设备时给分步引导（含「下一步扫码」指引）。
- **衔接**：复用现有导入解析（`/config/import`）与设备创建接口，仅新增批量循环与逐条错误汇总。
- **依赖**：无。
- **验收**：见 V6。
- **实际实现**：批量导入没有复用 `/config/import`（它要求一份含 `[Interface]` 的完整 wg-quick
  文本、且只回传成功总数）。改为新增 `POST /peers/import`：前端把多行文本解析成结构化列表并
  预览，后端逐条创建、**逐条回传成功/失败原因**（重复识别码、格式非法都能定位到具体哪一行）。
  为满足「导入 100 台 ≤ 10 秒」，把落库逻辑从 `CreatePeer` 里抽出为不触发收敛的 `createPeer`，
  批量时最后统一收敛一次（否则 100 台会触发 100 次全量收敛）。新建向导在「添加设备」抽屉内做
  分步（选用途 → 填信息 → 扫码），最后一步**内嵌二维码**，不再跳到另一个弹窗。

#### P1-4 全局搜索与快捷跳转（已完成）
- **目标**：一个入口搜连接与设备，直接跳到对应页面并打开详情。
- **衔接**：纯前端，读已有列表数据。
- **依赖**：无。
- **实际实现**：新增顶栏搜索组件 `components/GlobalSearch.vue`，连接与设备统一检索
  （名称/备注/分组/识别码/所属连接），支持 `Ctrl/⌘ + K` 唤起；数据在首次聚焦时拉取并缓存 30 秒。
  跳转沿用已有的 query 约定并扩展：连接用 `interfaces?edit=<id>`、设备用 `peers?iface=<id>&edit=<id>`，
  目标页监听 query 变化后自动打开对应的详情抽屉（页面已挂载时也能生效）。

### P2 —— 0.9.0「兼容性与账号安全」

#### P2-1 用户态回退（已完成）
- **目标**：内核无 WireGuard 模块时仍能工作。
- **衔接**：`Backend` 接口已有三个实现（kernel/mock/预留 userspace），新增实现即可；「系统维护 → 运行环境」已展示工作模式。
- **依赖**：无。
- **风险**：R6（体积与行为差异）。
- **实际实现**：
  1. **先抽出设备驱动层**（`internal/wgback/driver.go`）：把「设备创建 / 节点读写」的差异收敛到一个
     `wireGuardDriver` 接口（`Ensure` / `Read` / `Configure` / `Delete` / `List` / `Identify` /
     `ForeignSupported`），配置载体沿用 `wgtypes`。MTU、地址、起停、策略路由、NAT、转发策略
     这些安全规则只保留**一份**实现 —— 两种模式的差异因此只可能出现在「怎么和 WireGuard
     说话」这一层，不可能漂移到三条铁规则上。
  2. **内核驱动**（`driver_kernel.go`）：rtnl 建网卡 + `wgctrl`（generic netlink）读写，与改造前行为等价。
  3. **用户态驱动**（`driver_userspace.go`）：`wireguard-go` + TUN，配置走 UAPI 文本协议。
     UAPI 编解码自己实现（`uapi.go`）：wireguard-go 只公开「整包 set」一个入口，
     拿不到「只改某个字段」的能力，而**增量下发**正是防抖动的关键（见 `peerdiff.go`）。
     UAPI 同样是**只增不换**：绝不输出 `replace_peers`（与内核模式的 `ReplacePeers` 等价，
     都会删光重建、摧毁会话密钥与动态学到的对端地址），没有变化的节点压根不进文本。
  4. **选择与回退**：默认自动 —— 内核可用就用内核；内核明显缺失但系统有 `/dev/net/tun` 时
     直接使用兼容模式；「模块文件在、真正建网卡时才被拒」的系统交给运行时回退：
     `Ensure` 返回 `errBackendUnsupported` 时切到用户态。回退时机刻意选在**创建接口**这一步
     —— 此时尚未建出任何内核网卡，不存在「半个内核态 + 半个用户态」的混合局面；
     切换后一次性清空回退句柄，避免来回横跳。`FNWG_BACKEND=kernel|userspace|auto`
     可强制指定，作为自动判断出错时的逃生舱；显式指定后不再自动切换。
  5. **兼容模式的安全边界**：用户态网卡同样是 TUN，无法与其它应用的 TUN 区分，
     因此 `ForeignSupported()` 报告 false —— 「疑似残留网卡」恒为空列表、删除网卡一律拒绝。
     宁可漏报残留，也不误删用户其它网卡。
  6. **能力如实上报**：「系统维护 → 运行环境」的工作模式取**实际生效**的后端（回退后即为
     `userspace`）；内核模块不可用但兼容模式可用时只提示「正在使用兼容模式」（警告级），
     两条路都断了才升级为错误。
  7. **切换数据面的收尾**：状态文件新增 `interface_backend`，记住每张网卡由哪种实现创建。
     实现变了（例如系统升级后内核模块变得可用，或反过来）时，旧网卡既读不到配置也配不上去 ——
     此时明确「删掉重建」并在变更说明里写清原因，而不是抛一句「配置失败」让用户去猜；
     网卡是本应用自己的对象，重建只影响自己。升级前创建的历史接口没有这条记录，
     按原行为处理、不做重建。
     另外，运行时回退只在**当前驱动还没接管过任何设备**时允许发生：
     一旦已经建出设备再回退，就会留下「一部分连接走内核、一部分走用户态」的混合数据面，
     那比直接报错更难排查，因此宁可让这一轮失败。

#### P2-2 TOTP 二次验证（已完成）
- **目标**：管理员账号可开启动态口令登录。
- **衔接**：扩展现有登录流程与用户表；恢复码复用密钥托管。
- **依赖**：无。
- **实际实现**：自实现 `internal/totp`（**不引入 TOTP 库**，理由与 P1-1 自实现解析器相同：
  TOTP 本体只有「HMAC-SHA1 + 动态截断」两步，stdlib 足够，且 RFC 6238 附录 B 有官方
  测试向量可逐条断言）。登录拆成两步：口令通过后**不签发会话**，只下发一次性挑战
  （新表 `sys_totp_challenge`，5 分钟有效、5 次失败即作废）；动态口令或恢复码校验通过后
  才签发会话。挑战独立成表而不给 `sys_session` 加 pending 标记，是为了从结构上杜绝
  「未过二次验证的令牌被当成已登录会话」——那种写法漏判一处就是越权。
  允许 ±1 个时间步（±30 秒）漂移以容纳客户端时钟误差；失败计数并入既有的
  「IP+账号」限流键（挑战是随机令牌，故新增 `TOTPChallengeUser` 反查所属账号）。
  **与规划的偏差**：恢复码没有复用 `secretbox` 做加密落库，改为存 `argon2id` 哈希
  （与登录口令同一套算法，明文只在开启时返回一次）。理由：恢复码是「验证凭据」，
  哈希后可验证、不可还原，比「可解密的密文」更安全——加密存储意味着主密钥泄露即
  恢复码泄露，而且管理员或备份文件能取回明文。代价是无法再次查看，只能重新生成，
  这是通行做法（GitHub 等亦如此）。
  另：开启与关闭**都要**重新验证当前口令（关闭还额外要求一次动态口令/恢复码），
  因为两者都会改变账号的安全边界：被盗会话若能直接绑定新验证器或关掉二次验证，
  真正的所有者就被锁在外面了。

#### P2-2b 二次验证对齐官方（已完成）
- **目标**：把 0.9.0 已落地的 TOTP 补齐到飞牛官方 2FA 的体验水位 —— 官方有的「信任本设备」与账号管理能力。
- **依据**：飞牛 fnOS v0.9.18（2025-07-31）上线的官方 2FA，官方帮助中心明确支持「勾选信任本设备后免除第二步 OTP，并可在个人设置中查看和管理」。
- **决策记录**（经确认）：
  1. 受信任设备有效期 **30 天**；
  2. **保留一次性恢复码**，不做「安全邮箱紧急验证码」——后者需自建 SMTP，且官方开放 API 里**没有发信能力**（只有 `trim.system.getPlatformConfig` 与 `file.*`），借不到系统的邮件通道；
  3. 管理员重置用户二次验证、改密码登出其它设备 **都补齐**。
- **实际实现**：
  1. 新表 `sys_trusted_device`（只存令牌 SHA-256）；登录第二步可勾选「信任本设备，30 天内不再验证」，
     命中的设备登录时**跳过第二步直接签发会话**；设备名由 User-Agent 启发式解析（`Chrome · macOS`，
     不引入 UA 库），便于用户在列表里识别异常设备。
  2. 「用户菜单 → 二次验证」内可查看受信任设备（设备名 / 来源 IP / 最近使用）并撤销单个或全部。
  3. **作废时机**（关键安全约束，全部有回归用例）：改密码、关闭二次验证、管理员重置、
     管理员改他人密码 —— 一律清空该账号的受信任设备与相关会话。
     其中「关闭后重新开启，旧令牌不得复活」单独断言，因为漏掉它等于留一条后门。
  4. 管理员可在「账号管理」里重置某账号的二次验证（清 TOTP + 恢复码 + 受信任设备 + 在线会话）,
     这是用户把自己锁在门外时的正规救法。
  5. 受信任设备令牌与会话令牌**分属两个 Cookie**：退出登录不清设备信任（否则「记住本设备」等于白做），
     但改密码、关闭二次验证、撤销设备时会同步清除。
- **验收**：`TestTrustedDeviceSkipsTOTP`（含「设备令牌不能替代口令」这条越权断言）、
  `TestTrustedDeviceIsPerUser`、`TestTrustedDeviceRevokedOnSensitiveChanges`、
  `TestRevokeTrustedDevice`、`TestAdminResetUserTOTP`、`TestAdminResetPasswordKicksSessions`、
  `TestChangePasswordKicksOtherSessions`。

#### P2-4 接入飞牛统一网关（NAS 账号免密登录，0.8.20 已移除该能力）
- **目标**：登录页同时提供「飞牛 NAS 账号」与「自建账号密码」两种方式，前者免密。
- **官方机制**（`developer.fnnas.com` 核心概念 → 统一网关）：在 `app/ui/config` 用
  `gatewayPrefix` + `gatewaySocket` 注册入口，**请求先由 fnOS 校验用户会话**，再转发到应用
  `target` 目录下的 Unix Socket，并注入可信身份头 `X-Trim-Userid` / `X-Trim-Username` / `X-Trim-Isadmin`。
  二次验证与「信任本设备」**由飞牛侧全权负责**，本应用零代码。
- **⚠️ 硬前提**：manifest 必须声明 `os_min_version = 1.1.3100`。飞牛口径是「**声明这个版本即表示应用
  使用统一网关**」，它同时是网关能力的最低系统版本。若仍声明更低的值（如 `0.9.0`），飞牛按**旧模型**
  解析桌面入口，而入口配置里已没有 `protocol`/`port`，没有可用上游 —— 点图标当场 **502 Bad Gateway**，
  故障点全在声明里，应用自身（socket、端口、日志）看起来一切正常。
- **不采用的路线**：飞牛的 OAuth 服务（`/oauthapi/authorize` + `/v/api/v1/auth`）**不对外开放**，
  `trim.oauth_app` 只预置「影视」「相册」两个第一方应用，第三方无法接入。
- **已确认的边界**：网关模式启用后**关闭独立端口的密码登录**，端口降级为「安全码应急入口」。
- **⚠️ 最高风险点**：**只能在 Unix Socket 监听器上信任 `X-Trim-*`**。应用同时监听 TCP 端口，
  若在 TCP 上也信任这些头，任何人只要访问该端口就能伪造 `X-Trim-Isadmin: true` 冒充管理员。
  这对应官方安全红线第 1 条（绝不信任客户端传入的用户 ID）。
- **依赖**：P2-5（安全码后手）需先具备，否则关闭端口登录后一旦网关异常就彻底无入口。
- **实际实现**：
  1. **通道**：`fnwg-web` 额外监听 `${TRIM_APPDEST}/app.sock`（官方要求 socket 必须是应用 target 目录下的
     文件名），与端口监听**共用同一份路由** —— 业务逻辑只有一份，两条通道的差别仅限于「身份头是否可信」。
     启动时先 unlink 旧 socket 再 bind，bind 后放开文件权限：文件权限只能回答「能不能连上」，
     回答不了「是谁连的」，真正的准入在下一步。
  2. **身份可信性的三重判定**（缺一不可，`internal/api/gateway.go`）：
     ① 请求必须经 Unix Socket 到达（连接建立时就断言 `net.Conn` 是 `*net.UnixConn`，属连接层事实，无法伪造）；
     ② 该连接的对端进程身份必须在允许列表内（`SO_PEERCRED`，默认只信 root 与本进程用户，
     可用 `FNWG_GATEWAY_UIDS` 放行其它 UID）—— **单靠 ① 不够**：socket 是本机文件，
     别的第三方应用同样连得上来，没有这一步就等于把管理员权限发给本机所有用户；
     ③ TCP 通道上还有一道中间件把这些头**直接删除**，使「在端口上伪造身份」在结构上不可能，
     而不是依赖每处代码自觉。
  3. **身份映射**（`sys_gateway_identity` 表 + `service.GatewayLogin`）：以飞牛 **UID** 为唯一键，
     本地账号名固定为 `nas:<uid>`，角色按 `X-Trim-Isadmin` 映射（管理员 → admin，其余 → viewer），
     每次登录都同步一次 —— 飞牛侧撤权后本应用必须跟着降权。
     **不按用户名匹配**：那样一个叫 admin 的飞牛普通用户会直接对上本地管理员账号，是提权漏洞；
     同时禁止自建用户名包含冒号，避免两个命名空间撞车。
     映射账号的口令散列是一个**格式非法的占位值**，因此它永远不可能用密码登录。
  4. **登录方式开关**（P2-5 的第 3 层后手）：`both`（默认）/ `gateway_only` / `password_only`，
     放在「系统设置 → 登录方式」页签，能进飞牛桌面就能改回来。
     **防自锁**：只有**成功用过一次**飞牛账号免密登录之后，才允许关闭端口登录；否则拒绝并说明该怎么做。
     该键也被通用设置接口拒绝 —— 前端不展示它，不代表服务端可以接受它。
     安全码应急登录**始终可用**，不受登录方式影响。
  5. **子路径部署**：前端资源由 `vite base: './'` 相对加载、路由用 hash 模式，
     请求地址由 `frontend/src/api/base.ts` 统一按当前入口前缀拼出（`/app/fn-wireguard` 或空）；
     后端把同一套 API 与静态资源挂在 `/app/fn-wireguard` 下。
     于是**同一份产物在两种入口下都能正常工作**，包括 WebSocket。
  6. **打包配套**：Web 服务单元的 `ReadWritePaths` 增加 `${TRIM_APPDEST}`；
      安装脚本把 target 目录设为「同组可写 + sticky 位」—— sticky 位让 Web 进程只能建/删自己的 socket，
      动不了 root 拥有的 `fnwg-agent` 等二进制（少了这一位，被攻陷的 Web 进程可能替换掉下次以 root 启动的 agent）；
      卸载时一并清掉 socket 残骸。
    7. **真机验证发现并修复（0.8.8）**：真机上「从飞牛桌面打开即免密进入」整条不通，免密从未成功过一次，
      于是「关闭端口登录」的防自锁校验永远通不过，而界面只会提示「请先从飞牛桌面打开一次」——
      这句话在那台机器上**无论如何都做不到**。根因在 6 的启动参数里漏了一项：`TRIM_APPDEST` 只存在于
      安装脚本的进程环境，**systemd 不会继承**，Web 服务单元又没把应用目录显式传进去，进程于是按默认值 `.`
      取址，把 socket 当成相对路径（systemd 下即 `/`）去建 —— 普通用户对 `/` 没有写权限，bind 直接失败，
      统一网关入口整个不存在，而日志里只有一句容易被忽略的警告。修复分两层：
      ① 单元与 pidfile 两条启动路径都显式传 `--appdest ${TRIM_APPDEST}`；
      ② `Config.AppSockPath` 在拿不到绝对应用目录时退到**可执行文件所在目录**
      （二进制就装在 target 里，这条事实与启动方式无关），使这个位置不可能再被算错。
      同时补上可观测性：`/auth/login-mode` 回报 `gateway_socket` 与 `gateway_diagnosis`，
      设置页据此区分「入口没起来」（环境问题）与「入口正常但还没走过」（确实该去点一次），
      不再把用户送去反复做一件做不到的事。
    8. **登录页不再对「看不到飞牛入口」保持沉默（0.8.9）**：起因是登录方式默认为 `both`
      （两种都允许），用户却只看到账号密码表单，只能反过来问「为什么没有飞牛的登录」——
      问题不在开关，而在页面没说自己观察到什么。`gateway.available` 只表达「本次请求带着
      飞牛身份头」，于是按两种事实分别给出指引：`gateway.entry` 为假（请求走的是端口，网关
      没经由 socket）提示「免密只在从飞牛桌面打开时可用」，为真却无身份头（刷新过页面、
      链接被复制到别处打开）提示「回飞牛桌面重新点开」。凡是「入口存在但这次用不上」的情形，
      都应能就地读到原因，而不是让用户去猜功能是没做还是坏了。
   9. **换了入口模型却没同步声明（0.8.12）**：桌面入口从端口模型改为统一网关后，从飞牛桌面点开报
     **502 Bad Gateway**，而应用自身一切正常 —— socket 已按 target 目录正确建立、端口入口可访问、
     日志无异常。根因不在代码：manifest 的 `os_min_version` 还是网关能力之前的 `0.9.0`，飞牛据此仍按
     旧模型解析入口，可入口配置里 `protocol` 已留空、也没有 `port`，拼不出上游，于是 502。
     修复即上面那条硬前提（改为 `1.1.3100`）。教训：**换入口模型时必须同时核对声明** ——
     只改 `app/ui/config` 而不改 manifest，两边各自看都「正确」，故障恰好落在它们之间。
     10. **免密登录整套移除（0.8.20）**：**保留统一网关入口本身**（从飞牛桌面点图标仍经
     `/app/fn-wireguard` + `app.sock` 打开本应用），移除的是「凭网关注入的身份直接进应用」这件事：
     ① `X-Trim-*` 身份头不再被解析（连常量都不再存在，TCP 通道也就不需要「删除身份头」的中间件了）；
     ② `sys_gateway_identity` 映射表、`nas:<uid>` 账号与「飞牛管理员→管理员 / 普通用户→只读」的同步规则；
     ③ 登录方式开关（`both` / `gateway_only` / `password_only`）及「没验证过免密就不许关端口」的防自锁校验，
     连同对 `onboarding`、通用设置接口的连带限制；
     ④ 账号列表/顶栏的「飞牛账号」标注、`display_name`/`source`/`trim_uid` 派生字段，以及
     由此而来的「改密码 / 开二次验证」只读限制（这些限制的存在理由已经消失）。
     现在只有一种登录方式：**本应用账号密码**；忘记密码走安全码应急登录，管理员也可用 `fnwg-cli` 重置。
     两条通道的权限完全相同，进入任何一条都必须先登录。
     **仍然保留**的部分（与身份无关）：`gatewayPrefix` 子路径部署与两条通道共用同一份路由、
     WebSocket 握手的网关通道判定（0.8.17 修的「飞牛桌面下实时状态连不上」靠的就是「连接来自 socket
     且对端身份已核验」这个**通道事实**，不是身份头）、以及 `/auth/state` 继续上报 `socket_ready` ——
     它是安装/升级脚本发现「socket 没建起来、点图标会 502」的唯一依据（0.8.16）。
     为什么移除：免密把「谁能进来」交给了外部系统注入的请求头，为此付出的复杂度（身份头可信性的三重判定、
     映射按 UID 而非用户名的提权规避、防自锁开关、两套登录路径各自的说明与自检）远超它省下的那一次输入。
     **兼容范围**：只承诺与正式版本（main，当前 0.8.1，从未包含免密登录）兼容。开发分支上试装过的构建
     不必专门处理 —— 那些库里会留下一张没人再读的 `sys_gateway_identity` 映射表和几个 `nas:<uid>` 账号，
     不报错也不影响使用，需要时在「系统设置 → 账号管理」里删掉即可；因此**没有**为它们写迁移代码。
     用户名的冒号限制也一并去掉：它当初只为保护那套映射命名空间，映射没了，限制就没有存在理由。
  11. **桌面图标 502、而端口与进程一切正常（0.8.22）**：升级报成功、Web 进程此后从未重启、
     端口可正常访问、日志里只有一次启动记录，唯独 `app.sock` 不存在（目录 mtime 停在启动那一刻）。
     根因在启动脚本，与网关、网络、权限都无关：授权命令 `fnwg_socket_fix_cmd` 末尾跟着一句
     `rm -f app.sock`，而它的调用链之一是 `fnwg_prepare_dirs` ← `cmd/main start`
     （应用中心点「启动」）。**在应用已经运行时再点启动**，顺序就是：删掉 socket →
     `systemctl start fnwg-web`（对已运行的单元是空操作，不跑 `ExecStartPre`、也不重启进程）→
     只查端口的 `fnwg_wait_health` 通过 → 报「启动成功」。删除与创建落在同一分钟内，
     所以外表看什么都没发生过；而升级收尾的检查跑在删除之前，因此升级也确实是「成功」的。
     修复：① 授权命令拆成 grant（只授权，绝不碰 socket 文件）与 prestart（授权 + 清残留 socket，
     只用于单元的 `ExecStartPre` —— 那里删完紧接着就 bind，中间没有空档）；
     ② `cmd/main start` 与 `config_callback` 改用 `fnwg_ensure_gateway_ready`（端口与入口一起查，
     失败自动修一次再判）；③ `/auth/state` 的 `socket_ready` 改为以**文件事实**为准，
     不再只是「进程启动时绑过一次」的记忆 —— 正是那个记忆让脚本的入口自查被骗过，
     自动修复的兜底永远不会触发。
     教训：**「让目录可写」与「删掉目录里的东西」必须分开** —— 前者是幂等授权，任何时机反复执行都安全；
     后者只有「确定紧接着会重建」时才成立，而「调用方之一是启动脚本」并不构成这个保证。
     加固（0.8.23）：入口不再只靠脚本在安装/升级/启动时检查一次 —— Web 进程每 15 秒自检一次
     （文件在且是 socket、**再真去连一次**，因此「文件被删」与「文件残留但没人监听」都能分辨），
     发现丢了就地重建，并把「曾失效」与「已恢复」都写进日志（只在原因变化时告警，不刷屏）；
     「系统维护 → 一键体检」新增该项，给出路径、状态与处置办法，不可用时按异常报出并可一键跳转。
     至此这类故障既不会静默，也不必再等人去修。

#### P2-5 防自锁后手（安全码 + CLI + 登录方式开关，已完成）
- **背景**：P2-4 选定「关闭独立端口登录」后，必须有退路，否则飞牛网关侧一旦异常就再也进不去。
- **三层后手**（经确认）：
  1. **安全码（已完成）**：首次初始化时生成并**强制确认保存**后才放行进入控制台
     （32 字节 → Base32 共 52 字符，约 256 位熵），只存 argon2id 哈希，
     生成失败时如实告知而非静默跳过；登录页新增「用安全码应急登录」，可顺带重置管理员口令。
     **一次性**：用后立即作废并下发新的一码（同样强制保存）。
     规整函数忽略大小写、分组连字符与空白 —— 52 字符的长串多半是抄录或粘贴进来的。
     单独成表而不放进 `app_setting`：放进设置表会被全量备份带走，等于把万能钥匙抄进备份文件。
     安全码不作为账号，而是**实例级凭据**，应急登录落在「第一个启用的管理员」上（停用的账号拿到会话也做不了恢复）。
  2. **`fnwg-cli` 用户管理（已完成）**：新增 `user list` / `user reset-password` / `user reset-2fa` /
     `security-code`，复用与界面完全相同的安全约束（重置口令即作废受信任设备与全部在线会话），
     操作以 `fnwg-cli` 身份写入审计日志。
  3. **登录方式开关（已随 P2-4 于 0.8.20 移除）**：原实现是应用内「系统设置 → 登录方式」页签，
     能进飞牛桌面即可切回自建账号模式，且启用「只用飞牛账号」前必须先**成功用过一次**免密登录。
     免密整体移除后，「可切换的入口」不再存在，这一层后手随之作废；安全码与 `fnwg-cli`
     两层后手保留不变，且安全码现在覆盖了原本需要它的全部场景。

#### P2-3 配置快照与一键回滚（已完成）
- **目标**：关键操作自动留快照，可查看差异并回滚。
- **衔接**：复用现有备份/还原与审计日志；回滚后由收敛引擎保证内核态一致。
- **依赖**：无。
- **风险**：R7。
- **实际实现**：
  1. 快照与用户手动备份**共用 `backup_record` 表**，靠新增的 `kind` 字段分流（`manual` / `imported` / `auto`）：
     备份列表只列 `manual`/`imported`，快照列表只列 `auto`（`ListBackupsByKind`），两者互不淹没。
  2. 关键操作前自动留档（`snapshotBefore`）：连接增删改/启停/轮换密钥、设备增删改与各类批量操作、
     内网域名增删改、系统设置修改、配置导入、备份还原——覆盖所有会改变期望态的动作。
  3. **不堆同样的文件**：留档前先与最近一份快照做指纹比对（清零公钥/在线/握手/速率等运行时字段后再比），
     内容一致即跳过；当前负载再走一遍 JSON 解码以保证空切片/空 map 的归一化与文件侧一致，
     否则「nil vs []」这种 JSON 序列化差异会被误判成「变了」。
  4. 默认只保留最近 50 份（`SettingSnapshotKeep`），超出部分的记录与文件一并清理。
  5. 差异对比（`SnapshotDiff`）按「连接 / 设备 / 内网域名 / 设置」分组，逐条给出新增/删除/修改；
     密钥类字段只提示「已更换」不显示前后值；域名用连接标识 + 公钥定位，避免改名被误判成「一增一删」。
  6. 一键回滚（`RollbackSnapshot`）只作用于 `auto` 快照（手动/导入的备份不允许走此路径），
     回滚前先为**当前**状态再留一份快照（滚错了能再滚回来），回滚后触发 `reconcile` 幂等收敛；
     收敛失败**明确报错并保留快照**，绝不静默留在半态。
  7. **配置回滚不带账号**：快照文件本身不写入账号（`users` 恒为空），回滚也不碰账号表——
     改密码往往正是因为旧密码可疑，把密码哈希回退等于重新打开一扇已知有风险的门。

## 七、技术难点与风险

| # | 难点 / 风险 | 说明 | 应对 |
|---|---|---|---|
| R1 | ~~同隧道内的隔离规则容易误伤~~ **0.7.0 已规避** | 原计划按 `iifname/oifname` 匹配，写宽了可能连 NAS 自身或回程流量一起丢 | 改为「源与目标都在隧道网段」的地址匹配：NAS 自身走 input、内网回程走放行规则，结构上不可能被命中（见[十](#十070-偏差补记)第 1 条） |
| R2 | 改范围要重新扫码，用户容易漏 | 设备侧 `AllowedIPs` 变更是客户端行为，NAS 无法远程生效 | 保存后弹窗强提示 + 设备列表标记「配置已过期」；提供一键重新生成二维码 |
| R3 | 通知拖慢或拖垮收敛循环 | 收敛循环 10 秒一次，Webhook 目标可能超时 | 通知走独立 goroutine + 队列；单次超时 ≤ 3 秒；同事件 5 分钟去重；失败只记日志不影响收敛 |
| R4 | DNS 接管与系统 DNS 冲突 | NAS 上可能已运行 DNS 服务（Docker 等） | 只绑定隧道内本机地址、只在专用表里做 DNAT；检测到冲突则明确提示而不是抢占 |
| R5 | DDNS 依赖外部服务与凭据 | 各家 API 差异大，凭据泄露风险 | 凭据用 `secretbox` 加密落盘，界面只显示掩码；失败重试并展示最近一次结果 |
| R6 | 用户态回退带来体积与行为差异 | 引入 `wireguard-go` 会显著增大二进制，且性能低于内核 | 仅在检测到内核不可用时启用；界面明确标注「兼容模式」，并提供一键切回 |
| R7 | 快照回滚可能停在半态 | 数据库回滚成功但内核下发失败（或反之） | 回滚后立即触发一次幂等收敛；失败时保留快照并报明确错误，绝不静默 |
| R8 | 历史流量落盘的写放大 | 高频采样会持续写盘，长期可能占满 | 降频采样 + 聚合落盘 + 明确保留策略（默认 90 天），并在维护页显示占用 |
| R9 | **安全边界漂移**（长期风险） | 功能变多后，容易出现「顺手改了系统规则」的回归 | 延续既有三条铁规则 + 每个新 nftables/netlink 能力都必须有穷举测试；CI 强制全量测试 |
| R10 | 不同 fnOS/内核版本行为差异 | nftables 与 netlink 在旧内核上表现不同 | 沿用「多策略探测 + 探测失败必须说清原因」的既有模式，禁止静默失败 |

## 八、验收标准

> 全部为**可衡量**条目；真机验证时逐条勾选。`NAS` 指飞牛 NAS，`设备` 指扫码接入的手机/电脑。

### V1 设备间隔离（P0-1）
- 开启后：设备 A `ping` 设备 B **不通**；设备 A `ping` NAS 隧道地址 **通**。（真机待验证）
- `nft list table inet fn-wireguard` 中新增规则条数 == 预期条数（无多余规则）。
  → 规则对由纯函数 `NATPlan.IsolationRules()` 给出，条数在「系统维护 → 内网访问诊断 → 设备间隔离」直接显示（如「共 3 条阻断规则」），可直接与 `nft` 输出对照。
- 关闭后：表内规则数回到开启前（差值 0），且设备 A 与 B 恢复互通。
  → 关闭时整表按新决策重建（隔离规则消失）；内网访问也关着时整表删除。
- 回归测试覆盖「开启/关闭/切换连接」三种路径。
  → `TestPlanIsolationRulePairs`、`TestPlanIsolationCoversAllTunnels`、`TestPlanIsolationOffChangesNothing`、`TestStateIsolateTracking`。

### V2 按设备范围（P0-2）
- 设备配置里的 `AllowedIPs` 与界面设定**逐字符一致**。
  → 界面设定与配置渲染共用同一套推导（`clientAllowedIPs`），指纹也由同一份输入计算。
- 范围外的目标地址 `ping` 不通，范围内目标 `ping` 通。（真机待验证）
- 修改范围后，界面在设备列表标出「配置已过期」，并可通过一键重新生成二维码消除。
  → 设备列表新增「配置」列，点标签即打开扫码对话框，关闭后标记当场消失（`TestPeerConfigStaleLifecycle`）。
- 保存范围与 NAS 现有网段冲突时，保存被拒绝且提示指出冲突对象。
  → 保存期拒绝两类写法：写成默认路由、与其它连接的隧道网段重叠（`TestPeerScopeConflictRejected`）。

### V3 事件通知（P0-3）
- 四类事件（上线、离线、到期、配额用尽）在 **30 秒内**送达指定地址。
  → 上下线在下一次采样（2 秒）判定后立即入队；离线沿用统一的 3 分钟无握手窗口。
- Webhook 地址不可达时：收敛循环单轮耗时增加 **< 100 ms**（可在运行记录中核对）。
  → 投递走独立队列与 goroutine，`TestNotifyReturnsImmediately` 断言入队耗时 < 100 ms。
- 同一设备同类事件在 **5 分钟内不重复**发送。
  → `TestNotifyDedupeAndFilter`。
- 界面能显示「最近一次发送时间 + 结果」，失败原因可读。
  → 「系统设置 → 事件通知」显示最近一次结果并提供「发送测试通知」；失败同时进入全局异常清单（`TestDeliverFailureIsReadable`）。

### V4 访问控制冲突诊断（P0-4）
- 三类冲突各有一条可读提示，含冲突双方与建议值。实现对应关系：
  ① 设备范围 vs 隧道网段 → `scope_cross_interface`（其它连接）与 `scope_blocked_by_isolation`（本连接的隔离）；
  ② 隧道网段 vs 主机网段 → 沿用内网访问自检的「转发规则」项（`PlanNAT` 的 `SkipReason`）；
  ③ 范围互相矛盾 → `scope_default_route` 与 `scope_needs_lan_access`。
  → 每条结论点名连接与设备（`TestDiagnoseAccessConflicts`）。
- 无冲突时诊断清单显示「全部通过」，不产生误报。
  → `TestDiagnoseAccessNoFalsePositives`（含「停用的连接不参与诊断」）。

### V5 DNS 主机名（P1-1）
- 设备端 `nslookup <主机名>` 返回 NAS 隧道地址。
- NAS 自身 `/etc/resolv.conf` 与上游 DNS **未被修改**（改造前后 diff 为空）。

### V6 批量导入（P1-3）
- 导入 100 台设备耗时 ≤ 10 秒。
- 重复公钥 / 非法公钥被逐条拒绝，并在结果中给出可复制的失败清单。

### V7 用户态回退（P2-1）
- 内核无模块的环境下，设备握手成功、可访问 NAS。
- 「系统维护 → 运行环境」正确显示「兼容模式」。
  → 工作模式取实际生效的后端；兼容模式可用时健康清单只给警告级提示，不误报成错误。
- 兼容模式**不误删**用户其它 TUN 网卡。
  → 用户态驱动的 `ForeignSupported()` 恒为 false：残留列表恒为空、删除请求一律拒绝。
- 下发文本绝不含 `replace_peers`（与内核模式的 `ReplacePeers` 等价，必须同样禁止）。
  → `TestEncodeUAPISetNeverReplacesPeers`、`TestEncodeUAPISetOmitsUntouchedPeers`。
- UAPI 回显解析与内核模式同构（含未握手节点、多节点分段、密钥由私钥推导公钥）。
  → `TestDecodeUAPIGet`、`TestDecodeUAPIGetKeepsZeroHandshake`、`TestDecodeUAPIGetSplitsPeers`。
- 数据面实现记录跨重启保留，删除接口时一并清除。
  → `TestInterfaceBackendSurvivesReload`、`TestUnmarkManagedDropsBackendRecord`。

### V8 TOTP（P2-2）
- 开启后错误动态口令无法登录；恢复码可用；关闭需验证当前口令。
  → `TestTOTPEnableAndLogin`、`TestTOTPChallengeAttemptLimit`、`TestTOTPDisableRestoresPlainLogin`。
  其中两条越权断言最关键：口令通过但未过二次验证时 `Login` **不得**返回令牌；
  登录挑战**不得**能当会话令牌用（拿它访问受保护接口必须失败）。
- 原有口令登录路径不被破坏（关闭 TOTP 后行为与升级前一致）。
  → 关闭后 `Login` 直接返回会话、不再要求动态口令（同一测试内覆盖）。
- 动态口令算法本身正确。
  → `internal/totp` 用 RFC 6238 附录 B 的 6 条官方测试向量逐条断言。
- 恢复码一次性、且允许手抄时的书写容错（大小写、连字符、空格）。
  → `TestTOTPEnableAndLogin` 覆盖「用过的恢复码失效」与「小写去连字符仍可用」。

### V9 快照回滚（P2-3）
- 回滚后连接数/设备数与快照一致；`ip route show default` 与快照时一致。
  → 回滚覆盖连接/设备/内网域名/设置四项后触发幂等收敛；`TestSnapshotAutoCaptureAndRollback`
    断言回滚后连接数、监听端口与设备数回到快照值，且**回滚后再次比对差异为空**（回滚到位，而非「看起来回滚了」）。
- 回滚过程中人为中断，下一次收敛能自愈到一致状态（无残留内核对象）。
  → 回滚后立即 `reconcile`；失败时返回明确错误并保留快照以便重试（R7 的应对），绝不静默。
- 配置回滚**不触碰账号**，避免安全倒退。
  → `TestSnapshotExcludesAccounts`：快照文件不含账号，回滚后密码哈希与二次验证密钥保持回滚前的值。
- 关键操作各自留档、内容未变不重复留档、超出份数连文件一起清理、自动快照不淹没手动备份。
  → `TestSnapshotPruneKeepsLimit`、`TestSnapshotSkipsUnchangedConfig`、`TestSnapshotsStayOutOfBackupList`、
    `TestRollbackRejectsNonSnapshot`、`TestBackupCoversDNSRecords`。

## 附：发布与分支约定

- **分支模型**：日常开发一律在 `dev` 分支；新版本定型后合入 `main`，在 `main` 上打 `v*` tag 发版。`main` 只放已定型的版本。
- **每次可感知的改动都升级版本**：只要安装包内容会变，就先 bump 版本再打包，保证设备上装的版本、日志里报的版本、更新说明三者一致。
- **发布载体**：GitHub Release + 双架构 `.fpk` 安装包（`amd64` / `arm64`），由 `git tag v*` 触发 `.github/workflows/release.yml` 自动构建。
- **补丁版本**（`0.6.0 → 0.6.1`）：只修缺陷、不改行为，用户无感升级。
- **次版本**（`0.6 → 0.7`）：新增一组完整功能，界面或行为有可感知变化。

```bash
git checkout dev                 # 日常在 dev 开发
git push origin dev

git checkout main && git merge dev    # 新版本定型后合入
git push origin main
git tag -a v0.7.0 -m "..." && git push origin v0.7.0   # 触发 Release
```

## 九、已发布版本功能规格（摘要）

> 详细说明见各版本 Release 说明与 `apps/fn-wireguard/manifest` 的 changelog。

### 0.3.x —— 安全加固、多连接、异地组网

- 路由安全铁规则：默认不改系统路由；需要下发时写入专用策略路由表 `51888` + `ip rule`，系统主路由表零改动。
- 接口接管保护：不接管、不删除非本应用创建的网卡。
- 连接之间自动错开专用地址与端口，创建前跨连接冲突校验。

### 0.4.0 —— 稳定性与残留治理

- 收敛改为按差异增量下发节点，修复隧道周期性抖动。
- 疑似残留网卡检测与安全清理；自动命名避开内核已存在的网卡名。

### 0.5.x —— 内网访问

- 连接级「允许设备访问家里内网」，专用 nftables 表做源地址改写，只匹配隧道网段。
- 内网访问逐层诊断；出口网卡三重探测（全表扫描 + 内核路由查询 + `/proc`）。

### 0.6.x —— 界面整合与状态可见性

- 独立「系统维护」入口；系统设置只保留改配置类功能。
- 全局异常可见机制：顶栏状态栏、异常横幅、总览状态卡、连接页行内提示（同源判定）。
- 应用图标去除白边；文档重构（README + 本文档）。
- 0.6.1 工具名称统一为「WireGuard 管理工具」。

### 0.7.0 —— 访问控制与事件通知

- **设备间隔离**：连接级开关，禁止设备互访（跨连接一起隔离），设备仍可访问 NAS 与内网。
- **按设备的通行范围**：自定义范围可直接点选探测到的家里网段；保存期拒绝「写成全部流量」与「指向另一条连接」两类写法。
- **配置过期可见**：改动对外地址/DNS/通行范围后，设备列表标出「需重新扫码」，点一下即重新生成并消除标记。
- **事件通知生效**：设备上线/离线/到期/流量用尽推送到 Webhook，支持 JSON/纯文本两种格式与逐事件开关，界面显示最近一次结果并可发送测试通知。
- **访问控制冲突诊断**：范围、开关、隔离三项设置互相矛盾时给出结论、冲突双方与建议（含历史数据兜底）。

### 0.7.1 —— 事件通知收尾

- 系统设置新增独立「事件通知」页签（接入设置 / 事件通知 / 账号管理 / 备份还原 / 关于），通知配置与接入配置各自保存。
- 推送格式支持 **Markdown**：钉钉、企业微信、飞书群机器人按各自报文结构投递（飞书发交互式卡片，异常红色头部、正常绿色头部）；响应里的错误码非 0 视为失败并给出原因（`errcode` 对所有格式检查，飞书的 `code` 仅在确认是飞书时检查，避免把通用接收端的 `code=200` 误判为失败）。
- 可配置事件补齐到 **8 类**并分组：设备（上线/离线/到期/流量用尽）、连接（中断/恢复）、系统（配置下发失败、残留网络自愈）。
- 事件开关改为「记录被明确关闭的事件」：以后新增的事件默认开启，不再出现「新事件静默不生效」。
- 「最近一次」记录里可展开查看**实际发出的内容**，接收端不显示消息时可直接对照排查。

## 十、0.7.0 偏差补记

> 按「每版固定动作」第 5 条记录实际实现与规划的差异，便于后续版本估工时不再踩同样的坑。

| # | 原规划 | 实际实现 | 原因 |
|---|---|---|---|
| 1 | P0-1 用 `iifname 隧道 && oifname 隧道 → drop` | 改为「源与目标**都**落在隧道网段 → drop」 | 地址匹配精确等价于「设备之间互访」：访问 NAS 走 input 路径、访问内网走放行规则，都不会命中。不需要猜接口名，R1 担心的「误伤 NAS 自身与回程流量」从根上消失，也无需额外放行。代价是设备侧表现为超时而非立即拒绝 —— 用 drop 是为兼容旧内核（转发路径上生成 ICMP 依赖 conntrack 与内核版本） |
| 2 | P0-3「设置项不再新增字段」 | 新增 `notify_events`（逐事件开关）与 `notify_format`（JSON/纯文本） | 「配了就全推」在设备多时会被上线消息淹没；纯文本是自建推送服务（ntfy 等）的硬需求。`notify_webhook` 本身仍复用旧字段 |
| 3 | P0-2「给单个设备指定只能访问哪些网段」 | 复用既有 `route_mode=custom` + 新增配置指纹与保存期冲突校验 | 该模型 0.5 起已存在，真正缺的是「改完要重新扫码」的可见性与保存期的拦截 |
| 4 | P0-4 三类冲突 | 实际四类（多一类「隔离与通行范围互相抵消」） | 这是两项新功能组合后最容易踩的坑，且现象完全不可见（设备之间就是不通） |
| 5 | V3 要求「连接异常」也推送 | 0.7.0 未做；**0.7.1 已补上**（「连接中断 / 恢复」，并一并补齐「配置下发失败」与「残留网络自愈」） | 0.7.0 当时判断与设备上下线重合、且已被全局异常清单覆盖；但「不主动打开界面就发现不了」才是通知的真正价值，故补做 |

顺带完成的两处清理：

- 上下线判定的 3 分钟阈值此前在收敛引擎与状态缓存里各写一遍，现统一为 `model.OnlineWindow`；
- 通知地址一律脱敏展示与记日志（令牌常带在 URL 路径里），失败原因也不回显完整地址。
